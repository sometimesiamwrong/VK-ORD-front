# Безопасность и хранение токенов

## Архитектура аутентификации

Наше приложение использует двухтокеновую систему аутентификации:

### Access Token
- **Где хранится**: В памяти (Zustand store)
- **Почему**: Минимизирует риски XSS-атак, так как токен живет только в рамках сессии браузера
- **Время жизни**: Короткое (обычно 15-30 минут)
- **Использование**: Отправляется в заголовке `Authorization: Bearer <token>` при каждом API запросе

### Refresh Token
- **Где хранится**: В браузерных куках
- **Почему**: Куки персистентны и переживают перезагрузку страницы, при этом защищены флагами безопасности
- **Настройки безопасности куки**:
  - `Secure: true` - передача только по HTTPS
  - `SameSite: Strict` - защита от CSRF-атак
  - `Expires: 30 days` - срок хранения 30 дней
- **Время жизни**: Длительное (обычно 7-30 дней)
- **Использование**: Автоматически отправляется при запросе `/api/auth/refresh` для получения нового access token

## Процесс аутентификации

### 1. Вход (Login)
```
Клиент → POST /api/auth/login
Сервер → { token, refreshToken }
Клиент → Сохраняет token в памяти, refreshToken в куках
```

### 2. API запросы
```
Клиент → GET /api/users/me + Authorization: Bearer <token>
Сервер → 200 OK + данные
```

### 3. Автоматическое обновление токена (401 Unauthorized)
```
Клиент → GET /api/users/me + Authorization: Bearer <expired_token>
Сервер → 401 Unauthorized
Клиент → POST /api/auth/refresh + { refreshToken } из куки
Сервер → { token, refreshToken }
Клиент → Повторяет оригинальный запрос с новым token
```

### 4. Выход (Logout)
```
Клиент → POST /api/auth/logout
Клиент → Очищает token из памяти и refreshToken из куки
```

## Безопасность

### Защита от XSS
- Access token хранится в памяти, не доступен для скриптов после перезагрузки
- Refresh token в куках с флагом `Secure` (только HTTPS)

### Защита от CSRF
- Куки с флагом `SameSite: Strict`
- Refresh token дополнительно отправляется в теле запроса

### Защита от перехвата
- Все запросы только по HTTPS (флаг `Secure`)
- Короткое время жизни access token минимизирует окно уязвимости

### Автоматическое обновление
- При истечении access token автоматически запрашивается новый
- Пользователь не замечает процесс обновления
- При неудачном обновлении - редирект на страницу входа

## Файлы реализации

- `src/utils/cookies.ts` - утилиты для работы с куками
- `src/auth/tokenStore.ts` - хранилище токенов
- `src/auth/hooks.ts` - хуки аутентификации
- `src/api/http.ts` - HTTP interceptor с автоматическим обновлением

## Конфигурация

### Время жизни refresh token в куках
Настраивается в `src/auth/tokenStore.ts`:
```typescript
const REFRESH_TOKEN_EXPIRY_DAYS = 30 // 30 дней
```

### Настройки безопасности куки
```typescript
setCookie(REFRESH_TOKEN_COOKIE, token, {
  expires: REFRESH_TOKEN_EXPIRY_DAYS,
  secure: true,           // Только HTTPS
  sameSite: 'Strict',     // Защита от CSRF
})
```

## Требования к серверу

Сервер должен:
1. Возвращать `refreshToken` в ответе на `/api/auth/login` и `/api/auth/register`
2. Принимать `refreshToken` в теле запроса `/api/auth/refresh`
3. Поддерживать CORS с `credentials: true` для работы с куками
4. (Опционально) Также может отправлять refresh token в httpOnly куках для дополнительной безопасности

## Миграция с предыдущей версии

### Что изменилось
- Refresh token теперь хранится в куках вместо состояния страницы
- Токен переживает перезагрузку страницы
- Добавлена автоматическая очистка токенов при выходе

### Совместимость
- Если сервер не отправляет `refreshToken` в теле ответа, но отправляет в httpOnly куках, всё будет работать благодаря `withCredentials: true`
- Если сервер отправляет оба варианта, приоритет у явного значения в теле ответа
